# Повторный взлёт в Metal SITL: диагностика и исправление

Проверено 15 ноября 2026 года на Apple M5, PX4 v1.15.4 из образа
`ilyawwww/sverk-ros2:v1.9-sim`. Запуск: `./sim.sh start metal`.

## Воспроизведение до исправления

В одной сессии выполнялся тот же Python API, что в пользовательском коде:

```bash
docker cp simulation/tests/check_repeat_flight.py sverk_sitl:/tmp/check_repeat_flight.py
```

```bash
docker exec sverk_sitl bash -ic 'python3 /tmp/check_repeat_flight.py'
```

Первый взлёт на 2 м и посадка завершались; второй `navigate_wait` возвращал
`Auto-arm/offboard failed`. OFFBOARD включался, но команда arm получала
от PX4 `Arming denied: Resolve system health failures first`, затем API
завершал ожидание по таймауту. Отказ повторился в двух прогонах.

Обнаружены два отдельных пути к этому ответу.

## 1. Потеря периодических событий PX4

В одном прогоне `sensor_mag`, `sensor_gps` и `battery_status` перестали
обновляться около 32,6 секунды симуляции. IMU и барометр продолжали работать.
Заряд в последнем сообщении батареи был 100%: `Battery unhealthy` означал
не разряд, а устаревшие данные. В памяти процесса у задач сохранялись периоды,
но их события отсутствовали в достижимой цепочке `callout_queue`.

В POSIX HRT v1.15.4 блокировка снимается вокруг callback. В это окно другой
поток может повторно запланировать тот же элемент, после чего периодический
путь добавляет его снова и повреждает очередь. Этот механизм и его исправление
описаны в [upstream issue](https://github.com/PX4/PX4-Autopilot/issues/28922) и
[upstream commit](https://github.com/PX4/PX4-Autopilot/commit/9b62a1701de211fe8d9021f291d5668e8fb38b4e).
Совпадение механизма с потерянными событиями проверялось динамическим HRT-тестом:
конкурентный re-arm в старой сессии зависал; после backport тест прошёл с
`heartbeat=201 callbacks=106`.

`compat/px4-hrt-race.patch` переносит часть upstream-исправления для HRT:
рекурсивный mutex удерживается во время callback. Изменения upstream,
касающиеся времени жизни `WorkItem`, в этот backport не входят.
`compat/patch_px4_hrt.py` компилирует только `drv_hrt.cpp`, затем линкует PX4
с остальными объектами из исходного образа. Структуры полётных модулей не меняются.

Скрипт запускается автоматически из `compat/build.sh`. Он:

- допускает только известную сборку с git-hash `78bd1cc7c1e6472e535772d91a3ecbbfa1b5d507`;
- загружает исходники upstream v1.15.4 и проверяет SHA-256 архива;
- сохраняет исходный бинарник как `bin/px4.before-hrt-fix`;
- заменяет бинарник только после успешной компиляции и линковки;
- хранит исходники и manifest в `/home/sverk/.cache/sverk-px4-hrt`;
- повторно использует исправление, пока совпадают хеши бинарника и patch.

При первом запуске требуется доступ к GitHub для загрузки примерно 11 MB
исходников; полный ROS/PX4 стек заново не собирается. Для неизвестного образа
скрипт завершится ошибкой, оставив установленный бинарник без изменений.

Короткая регрессия запускается **внутри отдельной тестовой SITL-сессии**, куда
скопированы `tests/check_px4_hrt.sh` и `tests/px4_hrt_rearm.cpp` в одну папку:

```bash
bash check_px4_hrt.sh
```

На старой прошивке этот тест может повредить очередь или зависнуть; такую
тестовую сессию после него нужно остановить. Это не пользовательский шаг запуска.

## 2. Потеря ArUco после приземления

В другом прогоне батарея и магнитометр оставались свежими, но после посадки
пропадали `cs_ev_pos` / `cs_ev_yaw`; позднее PX4 отмечал позицию невалидной.
GPS уже был отключён штатным GPS-to-ArUco handoff. В журнале также появлялся
`Yaw estimate error`. Отключение магнитной коррекции (`EKF2_MAG_TYPE=5`) не
восстанавливало визуальную позицию; этот эксперимент отменён, осталось значение 0.

Контрольный кадр показал обрезанный верхний край посадочной метки. Камера
исходной модели находилась всего примерно в 47 мм над полом. Смещения около
8 см хватало для потери целой метки. Расширение объектива до 120° позволило
выполнить два полёта, но на третьем накопленное смещение снова вывело метку из кадра.
Опоры с исходной камерой и затем с камерой 120° позволяли пять полётов,
но проверка VIO после последней посадки всё ещё падала: это не принято за успех.

Итоговое исправление сочетает объектив **150° (2,6180 rad)** и четыре видимые
опоры с collision-геометрией в нативной учебной модели.
Опоры заканчиваются на 0,20 м ниже `base_link`, поэтому камера после посадки
остаётся примерно в 0,203 м над картой. Оптический TF и положение дальномера сохраняются.
Новые внутренние параметры объектива автоматически поступают из Gazebo через `CameraInfo`.
При клиренсе 0,2031 м, разрешении 1280×960 и HFOV 150° вертикальный обзор
пола составляет около 1,14 м. Это больше шага сетки плюс стороны метки:
0,6734 + 0,4 = 1,0734 м. Геометрическая проверка этого условия добавлена в тесты.
Расчёт относится к базовой ориентации относительно сетки; произвольные посадки
с большим наклоном/поворотом требуют отдельной проверки. Начальная высота spawn внешнего Gazebo — 0,25 м,
чтобы опоры не начинали внутри пола.

Это явное изменение геометрии и объектива **нативной учебной модели**,
а не точная копия клиренса и камеры реального обрика. Изображения и позиции по-прежнему поступают от
Gazebo и ArUco; синтетическая замена VIO не добавляется. Модели внутри
Docker/noVNC этими опорами не изменяются.

## Итоговая проверка

В итоговой проверке в одной чистой Metal-сессии выполнено **пять** взлётов
на 2 м и посадок подряд,
без пауз после disarm и без перезапуска PX4:

```bash
docker exec sverk_sitl bash -ic 'python3 /tmp/check_repeat_flight.py --cycles 5 --pause 0'
```

Приёмка требует для каждого цикла `reached takeoff height`,
`landed and disarmed` и `ready for next flight`: после disarm отдельно
проверяются свежая VIO, валидная позиция, ArUco/range fusion и сервисы. Проверки армирования, исходная магнитная коррекция и
ArUco-навигация оставлены включёнными. Пороги `COM_ARM_*` не ослаблялись,
force-arm не использовался. Все пять циклов прошли усиленную приёмку,
включая восстановление ArUco после последней посадки.

В прогоне ещё встречались отдельные предупреждения о задержанных позах
(`world_pose stale` / `dropped stale world_pose`); поток восстанавливался и
проверки после посадки проходили. Это не результат длительного теста стабильности.

Этот прогон проверяет вертикальный повторный полёт над исходной ArUco-картой.
Посадка вне зоны видимости меток по-прежнему может лишить дрон визуальной
позиции. Длительные миссии и остальные модели требуют отдельных проверок.
